# 不装任何 SDK，43KB 打造 Windows 原生维保查询工具：从接口逆向到性能调优的完整记录

> 需求很具体：给海康威视合作伙伴平台的「维保查询」做一个 Windows 本地小工具，**原生开发、速度第一**。
> 本文记录从环境侦察、技术选型、接口逆向、编码实现，到性能调优与 DPI 踩坑的全过程，所有数据均为本机实测。

---

## 一、缘起：为什么不用现成方案

官方平台本身就能查，但流程是：打开浏览器 → 找到查询页 → 输入序列号 → 等页面跳转 → 记结果。批量查几十个序列号时，这个流程会把人逼疯。

要做的工具，核心诉求只有三条：

1. **原生**：不要 Electron、不要浏览器套壳，双击就能用的 Windows 程序；
2. **快**：批量查询要真并行，等待时间要短，启动不能有"转圈感"；
3. **零负担**：不引入一堆运行时依赖，宁可体积小、启动快。

## 二、侦察：先看这台机器有什么

动手之前先做环境侦察，这一步直接决定了技术路线。（命令：`Get-Command` 逐个探测 + 检查系统目录）

| 工具链 | 结果 |
|---|---|
| dotnet SDK / 运行时 | ❌ 不存在 |
| MSVC（cl.exe）/ VS / vswhere | ❌ 不存在 |
| g++ / clang / MinGW / MSYS2 | ❌ 不存在 |
| rustc / cargo | ❌ 不存在 |
| git / scoop / chocolatey / winget | ❌ 不存在（winget 只是坏掉的商店别名） |
| Python 3.13.15（含 tkinter）/ Node.js | ✅ 存在 |

看起来"走投无路"，但有两个隐藏资产：

- **OS：Windows 10 IoT Enterprise LTSC，.NET Framework 4.8.09037** —— Windows 10/11 原生自带；
- **`C:\Windows\Microsoft.NET\Framework64\v4.0.30319\csc.exe`** —— 系统内置的 C# 编译器！

也就是说：**这台机器可以零下载、零安装，直接编译出 .NET Framework 的原生 WinForms 程序。**

## 三、选型：三条路线的取舍

| 路线 | 启动速度 | 体积 | 前置成本 | 结论 |
|---|---|---|---|---|
| A. 装 .NET 8 SDK + WinForms | ~0.2s | 自包含约 60~100MB | 下载约 200MB SDK | 可行但没必要 |
| B. 装 MinGW + C++ Win32 + WinHTTP | ~0.01s | ~100KB | 下载约 150MB 工具链 | 最"硬核"，但 JSON 要手写解析、开发风险高 |
| C. **系统自带 csc + .NET Framework WinForms** | **0.26~0.41s** | **43KB** | **零** | ✅ 采用 |

关键判断：**这个程序的耗时大头在网络上，不在进程启动上**。接口单次响应实测 0.5~1.5 秒，C++ 那 0.4 秒的启动优势完全无感；而 .NET Framework WinForms 用系统预置的、已 NGEN 过的程序集，启动实测 **264 / 393 / 407 ms**（三次冷启动，进程启动 → 主窗口出现），写代码的效率和健壮性却高得多。

> 💡 反思：优化要对着"瓶颈"去，而不是对着"听起来更快的技术"去。

## 四、接口逆向：先验证假设，再写一行代码

官方查询页点"查询"时的请求早已拿到（本文写作的前提）：

```
POST https://partners.hikvision.com/support/psp-api/repair/csp/product/getSnWarrantyInfo
Content-Type: application/json

{"serialNumber":"LA0000000"}
```

但我没有直接开写，而是**先用 PowerShell 的最小请求把接口打通，验证三个假设**：

```powershell
$body = '{"serialNumber":"LA0000000"}'
Invoke-WebRequest -Uri $uri -Method Post -ContentType 'application/json' -Body $body -Headers $headers
```

结论：✅ **匿名可查，无需登录、无需 Cookie**（游客态即可）。

### 坑 1：序列号竟然区分大小写

随手测了一组输入：

| 输入 | 响应 |
|---|---|
| `LA0000000` | `code:"000"`，返回完整数据 |
| `la0000000` | ❌ `code:"998"，msg:"序列号错误，请重新输入"` |
| `""`（空） | ❌ `msg:"请输入序列号"` |
| `ZZZZZZZZ` | ❌ `code:"998"` |

**案例数据**：小写输入被服务端直接拒绝。所以程序里所有序列号先 `ToUpperInvariant()`，并且从 UI 到 CLI 统一处理（这个细节如果漏掉，用户粘贴小写序列号会以为"设备查不到"，实际是大小写问题）。

### 坑 2：没有 charset 的响应头，是中文乱码的根源

响应头是：`Content-Type: application/json`——**没有 `charset=UTF-8`**。

按 HTTP 规范，`application/json` 缺省编码并不保证 UTF-8；.NET Framework 的 `HttpClient.ReadAsStringAsync()` 在这种情况下的回退编码并不可靠，中文直接乱码。解决方案是绕开字符串 API，**按字节读取后显式 UTF-8 解码**：

```csharp
byte[] bytes = await resp.Content.ReadAsByteArrayAsync();
string text = Encoding.UTF8.GetString(bytes);   // 服务端实际就是 UTF-8
```

这个 3 行决定是"中文永不出乱码"的关键。（顺带：调试期间我在 PowerShell 控制台看到的乱码，是另一回事——见第八节的"编年史"。）

### 字段清单

成功响应 `data` 里的字段（与官方页面 Sentry 遥测里的 query data 互相印证）：

| 字段 | 含义 | 示例值 |
|---|---|---|
| `labelModel` | 产品型号 | `DS-K1T342M` |
| `warrantyExpirationTime` | 保修截止 | `20280903` |
| `timeToOutOfInsurance` | 距离过保天数 | `705` |
| `serviceLevelName / serviceLevelMsg` | 服务级别 | 在线咨询服务 / 说明文案 |
| `productionImgUrl` | 产品图片（OSS 带签名，有时效） | `https://smp-prd-oss...png?Expires=...&Signature=...` |
| `configDesc / serviceContent / serviceEquity` | 配置 / 服务内容 / 权益 | 多为 `null` |
| `oldExchangeNewFlag / stopServiceFlag / hardDiskMaterialFlag / newBizFlag` | 各类业务标识 | `false` |
| `oemQueryState` | OEM 查询状态 | `否` |

**真实案例**（贯穿全文的验证样本）：

- `LA0000000` → 型号 `DS-K1T342M`，保修至 **2028-09-03**，剩余 **705 天**，状态"在保"
- `SN0000001` → 型号 `DS-2CD7A447FXJ-JGH (0832/4)`，保修至 **2028-07-31**，剩余 **671 天**

## 五、编码：C# 5 的"双手被绑住"

系统自带 `csc.exe` 版本是 4.0.30319（随 .NET Framework 分发），**只支持 C# 5**。这意味着：没有字符串插值 `$"..."`、没有 `?.`、没有 `nameof`、没有表达式体成员——写起来像穿越回 2012 年。

### 第一个编译错误（真实日志）

```
src\Api.cs(117,40): error CS1985: 无法在 catch 子句体中等待
src\Api.cs(124,40): error CS1985: 无法在 catch 子句体中等待
```

**`await` 不能出现在 `catch`/`finally` 里**（这是 C# 6 才放开的能力）。重试逻辑里本来优雅的 `await Task.Delay(...)` 只能改成同步 `Thread.Sleep(250 * attempt)`——反正跑在线程池线程上，不阻塞 UI。

### 编译脚本的一行关键参数

```powershell
& $csc /nologo /optimize+ /langversion:5 /codepage:65001 `
  /target:winexe /out:dist\HikWarranty.exe `
  src\Models.cs src\Api.cs src\Gui.cs `
  /r:System.Drawing.dll /r:System.Windows.Forms.dll `
  /win32manifest:app.manifest
```

- `/codepage:65001`：源码含中文注释与字符串，**不加这个，csc 会按系统 ANSI 代码页读源码，中文字面量当场乱码**；
- `/win32manifest`：嵌入 DPI 感知与 `asInvoker` 权限声明；
- `/langversion:5`：显式声明语言版本，避免误用新语法。

### 架构：一份核心，两个入口

```
src/Api.cs     接口客户端（查询 / 解析 / 重试 / 批量调度）   ← GUI 与 CLI 共用
src/Models.cs  数据模型 + 序列号文本解析                    ← 共用
src/Gui.cs     WinForms 界面（编译为 HikWarranty.exe）
src/Cli.cs     命令行入口（编译为 hikq.exe）
```

`Models.cs + Api.cs` 被编译进两个 exe：GUI 是 `winexe`（无黑框），CLI 是普通 `exe`（可脚本化）。**最终产物：GUI 43,520 字节，CLI 25,600 字节**——连一张表情包都比它们大。

额外收益：**CLI 就是现成的自动化测试床**。同一份核心逻辑，用命令行跑真实接口、导出 CSV/JSON，再做断言，比手动点界面高效得多。

### 并发调度器：30 行左右的核心

```csharp
var sem = new SemaphoreSlim(concurrency);
for (int i = 0; i < serials.Count; i++) {
    int idx = i;
    tasks[i] = Task.Run(async delegate {
        await sem.WaitAsync(ct);
        try { info = await client.QueryAsync(serials[idx], ct); }
        finally { sem.Release(); }
        results[idx] = info;              // 写死索引：天然保持输入顺序
        if (onOne != null) onOne(info);   // 实时进度回调
    }, ct);
}
```

几个细节：

- **结果按输入顺序回填**（`results[idx]`），界面表格不会"乱序跳动"；
- **`CancellationToken` 一路透传**，支持"停止"按钮和 Ctrl+C；
- **进度回调只负责推数据**，UI 侧用 `BeginInvoke` 回主线程刷新。

### 顺手填掉的两个坑

**1）表格"剩余天数"列要能排序。** 空值如果用 `""`（string），和 `int` 混在一列里排序会抛异常。方案：空值用 `int.MinValue` 作哨兵，渲染时用 `CellFormatting` 映射成空字符串，排序逻辑不受影响。

**2）DataGridView 批量刷新闪烁。** `DoubleBuffered` 是受保护属性，用反射打开：

```csharp
typeof(DataGridView).GetProperty("DoubleBuffered",
    BindingFlags.Instance | BindingFlags.NonPublic).SetValue(grid, true, null);
```

## 六、性能实录：从 19.1 秒到 4.5 秒

这是全篇最值得写的部分——**一次被数据推翻的误判**。

### 现象 A：第一次批量查询，慢得可疑

10 个序列号、并发 6，**总耗时 19.1 秒**。第一反应：并发生效了吗？是不是被 .NET 的连接池串行化了？

事实澄清：.NET Framework 的 `ServicePointManager.DefaultConnectionLimit` **默认每台主机只允许 2 个并发连接**——不改它，再多线程也会卡在连接池。我在客户端静态构造里先埋好了这一枪：

```csharp
ServicePointManager.DefaultConnectionLimit = 64;
ServicePointManager.Expect100Continue = false;            // 少一次 100-continue 往返
ServicePointManager.CheckCertificateRevocationList = false; // 省一次吊销检查
ServicePointManager.SecurityProtocol = SecurityProtocolType.Tls12;
```

### 埋点：给每条查询记一个耗时

光看总数猜不出瓶颈，于是给 CLI 加了 `-j`（JSON 输出），每条结果都带 `elapsedMs`。**同一批 30 条的数据分布**：整体平均 **1202 ms**，前/中/后 10 条平均分别为 1187 / 1375 / 1044 ms——**没有递增、没有排队迹象**，说明请求是均匀并行的，客户端调度没问题。

### 对照实验：并发数的甜蜜点

| 批次 | 耗时 | 说明 |
|---|---|---|
| 30 条 · 串行（c=1） | **23.09 s** | 约 0.77 s/条，作为基线 |
| 30 条 · c=4 | **6.72 s** | 3.4 倍加速 |
| 30 条 · c=8 | **5.47 s / 4.47 s** | 约 5 倍加速，最优 |
| 30 条 · c=16 | **7.88 s** | 反而变慢（服务端排队） |
| 10 条 · c=8 | **1.89 s** | 进程总耗时 2.24 s |

**结论**：默认并发定在 **8**。超过甜蜜点后，并发的收益被服务端的排队成本吃掉，**"把并发开大"不是免费的**。

而最初 19.1 秒的合理解释是：**冷启动效应**——首次 TLS 握手、DNS 解析、加上新编译 exe 的首跑开销。证据是同一命令第二次运行只要 **2.58 s**。

### 对症下药：预热

既然首条请求要为握手买单，那就**在程序启动时先把连接建起来**（后台静默执行，不阻塞界面）：

```csharp
Task.Run(() => _client.WarmupAsync());   // 启动即 GET 一次查询页
```

### 现象 B：单条查询 3.5~4 秒的"回马枪"

调优收尾时又撞见诡异数据：单条查询在-app 耗时 **3.56 / 3.65 / 4.01 秒**，而 10 条批量只要 1.89 秒——逻辑上不可能。

复测直接把结论改写：同一命令立刻重跑，单条 **0.52 / 0.55 秒**；3 条在同一时段跑出 **0.61 s** 和 **2.60 s** 两种结果。

**真相：接口的服务端响应本身在波动**（我们观测到同一序列号的单条耗时在 0.27 s ~ 3.4 s 之间摆动）。客户端能做的是：并行化、连接复用、重试兜底——这些都已到位，剩下的波动不属于客户端能消除的范围。

> 💡 教训：**遇到"不可能的数据"，先复测，再下结论。** 服务端不是常量。

### 冷启动 & 启动开销数据汇总

| 指标 | 实测 |
|---|---|
| GUI 启动 → 窗口出现（3 次） | 264 / 393 / 407 ms |
| CLI 纯启动（`--help`，不联网，3 次） | 40 / 35 / 36 ms |
| CLI 启动 + 连接预热 | 约 0.3~0.6 s（进程总耗时 − 应用内耗时） |
| 单条查询（应用内） | 0.52 ~ 0.55 s（正常时段） |

## 七、DPI 之谜：为什么截图只有 513×356

程序写完要验收界面，我写了个 PowerShell 脚本：启动应用 → `PrintWindow` 抓图。结果抓出来一张 **513×356 的图，只有窗口左上角**（完整窗口应是 1026×712 以上）。

### 诊断三连

| 检查 | 结果 |
|---|---|
| 应用 DPI 感知级别（`GetProcessDpiAwareness`） | **1 = system aware**（manifest 生效，好事） |
| 窗口所在屏幕 DPI（`GetDpiForWindow`） | **192（200%）** |
| 屏幕物理分辨率 | **3072 × 1920** |

### 根因

**截图用的 PowerShell（pwsh）进程自己是 DPI-unaware 的**。于是：

1. 它调 `GetWindowRect` 时，Windows 对 DPI 虚拟化——把 1026×712 的物理尺寸**除以 2** 报成 513×356；
2. 我按这个尺寸创建了位图，`PrintWindow` 却按窗口**真实物理尺寸**渲染；
3. 画布小了 4 倍，自然只剩左上角。

两个修复：

```powershell
[WinCap]::SetProcessDPIAware()   # 让抓图进程也感知 DPI，取到真实尺寸
PrintWindow($h, $hdc, 2)         # flag=2：PW_RENDERFULLCONTENT，完整渲染
```

修复后截图 **2026 × 1351**，完整、清晰。

### 更本质的修复：界面自己的缩放

截图过程中还发现：**WinForms 字体自动缩放只给了 1.48 倍，而 DPI 是 2.0 倍**（因为它按"字体度量比"算，而设计基线 (6,13) 是旧默认字体的值），导致控件偏挤。

**方案：关闭自动缩放，按 DPI 手动等比缩放全部布局**：

```csharp
AutoScaleMode = AutoScaleMode.None;
using (Graphics screen = Graphics.FromHwnd(IntPtr.Zero))
    _k = screen.DpiX / 96f;          // 200% 屏 → 2.0

ClientSize = new Size(S(1000), S(640));   // S(v) = round(v * _k)
```

字号仍用磅值（9pt 在 192 DPI 下系统自动渲染成 24px），坐标全部 ×`_k`。结果：逻辑 1000×640 的窗口在 200% 屏上物理 2026×1351，**比例与 100% 屏完全一致**：

## 八、调试手记：PowerShell 编年史

调优过程中最大的时间黑洞不是 C#，而是**用 PowerShell 观测 UTF-8 程序时的自我欺骗**：

1. **控制台乱码**：pwsh 默认按系统代码页（GBK）写管道，子进程输出 UTF-8 → 我这边看到满屏 。解决：命令开头先 `[Console]::OutputEncoding = [System.Text.Encoding]::UTF8`。**我一度以为程序输出乱码，其实程序一直是对的。**
2. **"JSON 被截断"疑案**：`Out-File` 存下来的 JSON 解析报 "Unexpected end"，折腾半天把锅扣在应用输出上。真相：`(Where-Object {...})[0]` 在**只匹配到一行时返回的是字符串标量**，`[0]` 取到的是**第一个字符** `[`，然后把这个字符拿去 `ConvertFrom-Json`……修正：`@(...)[0]` 强制数组化。
3. **中文变量名的反噬**：`"第$_次: ..."` 里 `$_:` 被当成"驱动器引用"直接解析错误，需要写成 `${_}`。

> 💡 教训：调试观测器本身会引入 bug。"工具说程序错了"之前，先验证工具。

## 十、可复用的经验清单

1. **先侦察环境，再选技术栈**——有时答案就藏在系统目录里（`csc.exe`）；
2. **速度要对着瓶颈优化**——网络 1s/条时，别为 0.3s 的启动差选一条更难走的路；
3. **先打通接口再写代码**——三个假设（鉴权、大小写、编码）用 10 行 PowerShell 验证完；
4. **.NET Framework 必改 `DefaultConnectionLimit`**（默认 2 连接/主机），否则并发表面无效；
5. **响应缺 charset 时，按字节 UTF-8 显式解码**，不要赌默认编码；
6. **并发有甜蜜点**：本案例 8 最优、16 反而慢，"开大并发"需要实验支撑；
7. **给每条请求埋耗时**，分布数据能瞬间区分"客户端排队"与"服务端变慢";
8. **DPI 三件套**：manifest 声明 + 截图工具 `SetProcessDPIAware` + 应用自身按 `DpiX/96` 手动手动缩放；
9. **CLI 作为 GUI 的测试床**：共享核心逻辑，让自动化验证成为顺手的事；
10. **调优前先复测**：3.5s→0.52s 的"回马枪"证明服务端波动比客户端 bug 更常见。

## 结语

这个项目的技术难度并不高，但把"零依赖、原生、快"三个约束同时满足，逼出了一条有趣的路：**用系统自带的编译器，写一个 43KB 的 Windows 原生程序**。真正的收获在于过程中那些被数据修正的判断——并发不是越大越好、首跑慢不必改架构、看到的乱码未必是程序的错。

如果后续要继续打磨，方向也很明确：给 GUI 加个图标、支持导出 Excel、把 GUI 也做成可脚本调用（`HikWarranty.exe sn.txt` 已经在做了），以及——**继续盯着服务端的波动做自适应重试**。
